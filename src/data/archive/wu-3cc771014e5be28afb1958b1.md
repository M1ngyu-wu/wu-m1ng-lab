# pwn--plt。

LT 是程序为了调用动态链接库（如 libc）里的函数而设置的一个“中转站”或“跳板”。
为了让你彻底明白，我们结合你前面的问题，从“为什么需要它”、“它怎么工作”以及“在 Pwn 里怎么用它”三个方面来解析。
1. 为什么需要 PLT？（延迟绑定机制）
在一个程序里，像 system、puts、read 这些函数，它们并不在程序自己的二进制文件里，而是在系统的 libc.so.6 动态库中。
在程序编译时，编译器并不知道 libc 最终会被加载到内存的哪个地址（因为 ASLR 随机化）。所以，程序不可能直接把 system 的绝对地址写死。
为了解决这个问题，Linux 引入了 PLT + GOT 机制：
• PLT（代码段）：存放一小段“跳转代码”。（地址固定，即使开 PIE 也只是相对偏移）
• GOT（数据段）：存放函数真实的绝对地址。一开始里面填的是 PLT 里的某个地址，等第一次调用后，动态链接器会把真实的地址写进 GOT 表。
2. 它是怎么工作的？
当你第一次调用 system 时，底层流程是：
1. 程序执行 call system@plt（跳转到 PLT 表里 system 对应的那一项）。
2. system@plt 里是一行跳转指令：jmp [system@got]。
3. 此时 system@got 里存的不是system 的真实地址，而是又跳回了 system@plt+6（下一行代码）。
4. 这段代码会去调用动态链接器（_dl_runtime_resolve），去 libc 里找到 system 的真实地址，并把它填入system@got 中。
5. 之后再调用 system，第3步就会直接跳转到真实的 system 地址，不再需要解析。
3. 在 Pwn（栈溢出）中，为什么你截图里的题用的是 system_plt = 0x08048460？
因为在你的题目中，程序是 No PIE（未开启地址随机化）。
这意味着：
• 程序自己的代码段地址是固定的。
• system@plt 这个“中转站”的地址在编译后就确定了，永远是 0x08048460。
• 而 system 在 libc 里的真实地址是随机的，我们不知道。
所以，我们通过栈溢出，把返回地址覆盖成了 system@plt。
当程序 ret 到这里时，它会去执行 system@plt 里面的跳转，最终通过 GOT 表，成功调用到 libc 里的 system 函数。
这就解答了你之前的疑问：
你跳到了 system@plt（中转站），虽然它最终会把你送到 system（工具），但它并没有帮你准备参数。system@plt 只是一个“跳板”，它只负责“跳”。参数（/bin/sh）依然需要你按照 32位/64位 的调用约定，手动在 Payload 里布置好。
4. 补充：PLT 和 GOT 在 Pwn 里的经典用法
• ret2plt：你截图里的这道题，直接跳 system@plt，因为它能成功调用 system。
• 泄漏 libc（GOT 泄漏）：真正的 ret2libc 中，我们不知道 system 地址。我们可以构造 Payload 跳转到 puts@plt，并且把 puts@got 的地址作为参数传给它。这样 puts 就会把 puts 在内存里的真实地址打印出来。我们拿到这个地址，减去已知的偏移，就能算出 libc 的基址，进而算出真实的 system和 /bin/sh 地址。
一句话总结
PLT 是程序里用来“呼叫”外部库函数的固定电话机（地址固定），GOT 是电话机的通讯录（一开始是空的，打过一次就记下真实号码）。 在漏洞利用中，跳转到 system@plt 就是拨通了这台电话，但你要让它说什么，还得你自己把台词（参数 /bin/sh）递过去。
